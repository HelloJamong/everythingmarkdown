# EverythingMarkdown 개인용 웹 서비스 전환 계획

- 작성일: 2026-09-10
- 수정일: 2026-09-11 — 최초 비밀번호 `.env` 설정, 원본/Markdown 독립 보관 정책, 마운트 로그 요구사항 반영.
- 상태: 구현 전 계획 초안. 코드·의존성·배포 환경은 변경하지 않았다.
- 이 파일은 Git으로 관리하는 웹 서비스 전환 계획이다. `.omx`의 로컬 작업 기록은 커밋하지 않는다.
- 참고 저장소: `../portable-jukebox`의 로컬 소스. 운영 중인 서비스나 원격 최신 버전을 검증한 것은 아니다.
- 표기: 아래 E 항목은 확인한 사실, 그 외 아키텍처·수치는 제안이다.

## 1. 요구사항 요약 및 기본 가정

목표: 개인 도메인의 HTTPS 웹페이지에 본인만 로그인하여 파일을 업로드하고 Markdown을 내려받는 Docker 서비스.

- 단일 소유자 계정, 단일 서버·앱 프로세스, 동시에 실행하는 변환 1개로 시작한다.
- 한 번에 파일 하나를 업로드한다. 기존 7개 형식을 유지한다.
- 로그인 → 업로드 → 상태 표시 → Markdown 원문 확인/복사/다운로드 → 삭제 흐름을 제공한다.
- 기존 CLI/GUI와 코어는 보존한다. 데스크톱 배포 확대보다 웹 MVP를 우선하며 기존 배포 자산을 삭제하지 않는다.
- `.env`의 최초 비밀번호로 단일 소유자를 초기화한다. 로그인 화면은 비밀번호만 입력하며 공개 가입 기능은 없다.
- 원본과 Markdown 각각 보관 여부(Y/N) 및 보관 시 최대 일수를 `.env`로 설정한다. 두 정책은 독립적이다.
- 보관 N은 영구 저장하지 않는다는 뜻이다. 원본은 변환 프로세스 종료 후 삭제하고, Markdown은 다운로드 제공을 위한 임시 수명만 둔다(아래 계약).
- HTTP 접근, 인증, 파일/변환 작업, 자동 정리와 운영 이벤트를 로그에 기록한다. 호스트 `./logs`를 컨테이너 `/logs`에 마운트한다.
- 회원가입, 사용자·역할 관리 화면, 장기 자동 로그인, 이메일 비밀번호 복구, 공유 링크, OCR, URL 변환, 일괄 변환, 공개 API, 다중 서버는 MVP 밖이다.
- 앞선 대화의 앞단 인증은 가능한 대안으로 남긴다. 이번 기본안은 참고 프로젝트처럼 **앱 자체 단일 계정 로그인**이다. 앞단 인증으로 이미 운영 중이라면 구현 시작 전 인증 단계만 교체한다. 두 인증 시스템을 동시에 새로 만들지 않는다.
- 실제 도메인, 기존 프록시 종류/위치, 호스트 CPU·메모리·아키텍처는 미확인이다. 계획에는 자리표시자만 쓰며 실제 DNS·서버 변경은 포함하지 않는다.

## 3. 목표 구조와 데이터 계약

```text
브라우저 → 개인 도메인 HTTPS → 리버스 프록시
                                  ↓ 내부 연결만 허용
                         FastAPI 웹 앱 (단일 프로세스)
                          ├─ 로그인·세션·CSRF
                          ├─ 템플릿 UI·작업 API
                          ├─ SQLite: 계정/세션/작업 상태
                          └─ 제한된 변환 자식 프로세스
                                └─ 기존 ConversionService
```

- 참고 스택 중 Python 3.12, FastAPI, Jinja2, bcrypt 및 세션 서명 패턴을 제안한다(E5–E7). UI는 작은 로컬 JS/CSS로 구성하고 SPA·Node 빌드·Tailwind·Alpine·HTMX 전체를 필수로 들여오지 않는다. 상태 폴링 개념만 재사용해도 된다(E11).
- 웹 런타임 후보: FastAPI, Uvicorn, Jinja2, python-multipart, bcrypt, itsdangerous. 테스트용 HTTP 클라이언트가 필요하다. SQLite는 우선 표준 라이브러리로 사용한다. 실제 의존성 추가와 호환 버전 고정은 구현 단계에서 검토하며 이번에는 설치하지 않는다.
- `web/` 하위에서 HTTP·저장소·작업 수명주기를 처리한다. 공통 코어에 웹 의존성을 넣지 않는다.
- 호스트 `./data`를 컨테이너 `/data`에 마운트하고, 원본은 `/data/uploads/<job_id>/input.<허용 확장자>`, 완성된 Markdown은 `/data/markdown/<job_id>/input.md`에 분리 저장한다. 작업 ID는 서버가 생성한다. 원래 파일명은 메타데이터로 보존하고 표시/다운로드 이름으로만 정규화하여 사용한다.
- 기존 코어 계약을 유지하기 위해 `/data/.work/<job_id>`를 생성하여 `ConversionRequest.launch_dir`로 전달하고 입력은 uploads 아래의 절대 경로로 지정한다. 코어의 임시 출력 `/data/.work/<job_id>/convert_result/input.md`를 변환 성공 후 같은 마운트의 최종 markdown 경로로 이동하여 게시한다. 전역 `chdir()`는 금지한다(E1). 완료 상태는 최종 파일 게시 후 저장하며, 게시/DB 갱신 사이 중단은 재시작 시 조정한다. 기존 최종 파일을 조용히 덮어쓰지 않는다.
- `.work`는 보관 대상이 아닌 변환 작업 공간이다. 실패/시간 초과/서버 중단 후 잔여 부분 파일을 정리한다. SQLite는 `/data/app.db`에 두고 파일 만료 정리 대상에서 제외한다. CLI/GUI의 기존 `convert_result` 계약은 변경하지 않는다.

호스트 저장 구조:

```text
data/
├── uploads/
│   └── <job_id>/input.pdf        # 업로드 원본
├── markdown/
│   └── <job_id>/input.md         # 완성된 Markdown
├── .work/                      # 변환 중 임시 작업 공간
└── app.db                      # 계정·세션·파일 메타데이터
logs/
├── access.log
└── audit.log
```

- 원본/Markdown 보관 Y/N과 최대 일수는 각각 uploads/markdown 파일에 적용한다. N도 처리·다운로드 중에는 이 경로를 일시 사용하며, 정해진 수명주기에 따라 제거한다. 한쪽 파일 만료 시 다른 저장 루트의 파일을 삭제하지 않는다.
- SQLite에는 단일 계정 해시, 만료/폐기 가능한 세션, 작업 ID·소유자·상태·만료 시각·안전한 파일 메타데이터만 저장한다. 문서 본문과 비밀번호 원문은 저장하지 않는다.
- 상태: `uploading → queued → running → succeeded | failed | timed_out`; 업로드 중단은 failed, 서버 재시작으로 중단된 작업은 interrupted. 결과 만료는 별도 result 상태(expired)로 표현하며 원본 보관 상태와 분리한다. 원본 또는 결과가 남아 있으면 정리에 필요한 작업 메타데이터를 유지하고, 둘 다 삭제되고 작업이 종료되면 제거한다. 감사 로그는 파일 보관 정책과 별도로 유지한다.
- 기본 제안값: 파일 25 MiB, multipart 요청 전체 26 MiB, 실행 1개, 실행 중+대기 최대 3개, 업로드 시간 120초, 변환 실행 시간 120초, 대기 만료 5분, 보관 N인 결과의 미다운로드 임시 수명 1시간, 정리 주기 5분. 하드웨어 시험 후 조정하며 성능 보장값으로 표기하지 않는다.
- 업로드 실제 바이트를 세고 요청 본문 파싱 전부터 제한한다. Content-Length와 확장자/MIME만 믿지 않는다. 거부·중단된 업로드 임시 파일도 삭제한다.
- 원본은 자식 프로세스 종료를 확인한 뒤 원본 보관 정책을 적용한다. 결과 다운로드 중에는 정리가 파일을 삭제하지 않도록 사용 참조와 유한한 전송 제한 시간을 둔다. 만료 후 새 다운로드는 거부하고 이미 시작한 전송 종료 뒤 정리한다. 작업 루트 밖 경로·심볼릭 링크는 거부한다.
- 렌더링된 HTML 대신 Markdown 원문을 escaped text로 표시한다. 미리보기 길이는 제한하고 전체는 첨부 다운로드로 제공한다. 변환률을 알 수 없으므로 가짜 퍼센트 대신 상태를 표시한다(E1, E11).

### 제안 엔드포인트

| 경로 | 계약 |
|---|---|
| `GET/POST /login` | 로그인 화면·검증, 로그인 CSRF 방어, 실패 시 일반화한 오류 |
| `POST /logout` | CSRF 검사, 서버 세션 폐기 |
| `GET /` | 인증된 업로드/최근 작업 화면 |
| `POST /api/jobs` | 인증·CSRF·한도 검사 후 업로드, 성공 202 + 작업 ID |
| `GET /api/jobs/{id}` | 소유자 검증 후 상태 반환 |
| `GET /api/jobs/{id}/preview` | 소유자 검증 후 길이 제한 Markdown 텍스트 |
| `GET /api/jobs/{id}/download` | 소유자 검증 후 첨부파일 반환 |
| `DELETE /api/jobs/{id}` | CSRF 및 소유자 검증, 실행 중 삭제는 409; 종료 작업 삭제 |
| `GET /healthz` | 민감정보 없는 내부 상태 확인 |

인증이 없는 API는 401, 잘못된 CSRF는 403, 없거나 타인 소유 작업은 404, 파일 초과 413, 지원하지 않는 형식 415, 용량/요청 한도 초과 429를 반환한다. 비동기 변환 실패는 상태와 안전한 오류 코드로 전달한다. 서버 절대 경로나 원시 parser 예외를 노출하지 않는다.

## 4. 인증·도메인·격리 계약

- 최초 계정 초기화는 `.env`의 `INITIAL_PASSWORD`로 수행한다. 계정이 없는 새 DB에서만 읽어 해시를 저장하며 기본 비밀번호는 없다. 첫 시작에서 값 누락/빈 값/예제 값은 시작 오류로 처리한다.
- 기존 계정이 있으면 `INITIAL_PASSWORD` 변경이나 컨테이너 재생성으로 비밀번호를 덮어쓰지 않는다. 재설정은 별도 컨테이너 관리 명령의 숨김 입력으로 수행하고 모든 기존 세션을 폐기한다. DB 유지 시 최초 설정 후 `.env`에서 비밀번호를 제거할 수 있다.
- `.env`는 암호화 저장소가 아니다. 저장소/빌드 컨텍스트에서 제외하고 소유자만 읽게 한다. Compose의 `env_file`로 런타임에 전달하며 이미지 build ARG에 넣지 않는다. 해시만 DB에 저장해도 호스트 `.env`와 컨테이너 환경에 설정값이 남을 수 있음을 운영 문서에 명시한다.
- 세션 서명 키를 secret 파일로 주입하고 누락/예제 키이면 시작을 거부한다. 해시/키/원본 파일이 이미지·로그·Git·빌드 컨텍스트에 포함되지 않게 한다.
- SessionMiddleware를 채택하면 쿠키에는 무작위 세션 참조만 넣고 서버에서 만료/폐기 여부를 확인한다. 로그인 시 참조를 회전하고 로그아웃/비밀번호 재설정 시 폐기한다. 기본 절대 만료 8시간, 장기 자동 로그인 없음.
- 쿠키는 서비스 전용 이름, host-only, Secure, HttpOnly, SameSite=Lax로 설정한다. 로그인·업로드·삭제·로그아웃의 CSRF 토큰과 Origin 검증을 수행한다.
- 로그인 실패는 계정·신뢰 가능한 클라이언트 주소 기준으로 제한한다(제안: 각 5회/분, 이후 429). 영구 계정 잠금은 두지 않는다. 비밀번호 길이 상한과 bcrypt 입력 처리 경계는 선택 버전 문서/테스트로 고정하며 조용한 잘림은 금지한다.
- 세션 쿠키는 암호화 저장소가 아니라 서명된 데이터이다. 문서/비밀번호를 넣지 않는다. 근거: [Starlette SessionMiddleware](https://starlette.dev/middleware/#sessionmiddleware).
- HTTPS는 프록시에서 종료한다. 같은 Docker 네트워크의 프록시라면 앱 포트를 publish하지 않고, 호스트 프록시라면 loopback에만 bind한다. 다른 서버 프록시라면 방화벽/사설망 규칙을 별도 확정한다.
- `FORWARDED_ALLOW_IPS`와 허용 Host는 실제 배포 경로만 신뢰한다. Jukebox의 IP 목록을 복사하지 않는다(E13). 근거: [FastAPI Behind a Proxy](https://fastapi.tiangolo.com/advanced/behind-a-proxy/).
- 비루트 실행, 불필요한 capability 제거, no-new-privileges, 루트 파일시스템 읽기 전용, 필요한 데이터/임시 경로만 쓰기 허용, CPU·메모리·PID·저장소 한도를 구성한다. 예시 자원값은 시험 후 확정한다.
- 변환 자식 프로세스에는 세션 키/비밀번호 환경을 전달하지 않는다. Linux 프로세스 자원 제한과 timeout 후 종료·회수까지 검증한다. 같은 컨테이너의 자식 프로세스는 완전한 보안 샌드박스가 아니다. 악성 문서 처리·다중 사용자 공개 서비스로 확대하면 별도 워커 격리/네트워크 정책을 추가해야 한다.
- OOXML 압축 해제 크기·항목 수 검사, 전체 저장소 사용 한도 및 실제 파일 정리를 둔다. 파일 업로드 접근 제어와 저장소/크기 제한의 근거: [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

### 4.1 `.env` 설정 계약 — 2026-09-11 요구사항

아래 값은 제안 기본값/예시이며 실제 `.env` 파일을 만들거나 비밀번호를 설정한 것은 아니다.

```dotenv
# 최초 DB 초기화 때만 사용. 예제 문구로는 시작하지 않음.
INITIAL_PASSWORD='CHANGE_ME_BEFORE_FIRST_START'

# 업로드 원본 보관
UPLOAD_KEEP=N
UPLOAD_RETENTION_DAYS=7

# 변환된 Markdown 보관
MARKDOWN_KEEP=N
MARKDOWN_RETENTION_DAYS=7

# 보관 N인 Markdown의 미다운로드 임시 수명(분)
TEMP_RESULT_TTL_MINUTES=60
CLEANUP_INTERVAL_SECONDS=300

# 파일 보관과 별개인 로그 정책(제안값)
LOG_RETENTION_DAYS=30
LOG_MAX_BYTES=10485760
LOG_BACKUP_COUNT=10
```

- `UPLOAD_KEEP`/`MARKDOWN_KEEP`는 공백 제거·대소문자 정규화 후 Y/N만 허용한다. 오타는 기본값으로 숨기지 않고 시작 오류로 처리한다.
- Y이면 대응 `*_RETENTION_DAYS`는 필수 양의 정수다. 0/음수/소수/누락은 거부한다. N이면 해당 일수는 사용하지 않으며 누락 가능하다. 임시 TTL·정리 주기·로그 제한은 양의 정수로 검증한다.
- 기간은 UTC 기준의 경과 시간이며 1일=24시간이다. 원본은 업로드 접수 완료 시각, Markdown은 변환 성공 시각에서 계산한다. 다운로드/조회로 기한을 연장하지 않는다.
- Y/N과 보관 일수는 각 파일 생성 시 스냅샷으로 저장한다. `.env` 변경 후 컨테이너 재생성부터 새 작업에 적용한다. 기존 파일에 소급하여 삭제/연장하지 않는다. 기존 파일은 원래 기한 또는 명시적 수동 삭제를 따른다.
- 원본 Y: 정상 접수된 원본은 변환 성공/실패와 무관하게 최대 일수까지 보관한다. 접수 거부·업로드 중단 파일은 Y라도 즉시 정리한다. 악성/용량 초과 입력을 보관하는 별도 저장소로 사용하지 않는다.
- 원본 N: 성공·실패·시간 초과·서버 재시작 중단 모두 변환 프로세스 종료 확인 후 정리한다.
- Markdown Y: 다운로드 여부와 무관하게 최대 일수까지 보관하며 기한 내 재다운로드를 허용한다. 실패 시 부분 출력은 Y라도 삭제한다.
- Markdown N: 다운로드할 수 있도록 임시 생성한다. 서버가 첫 다운로드 응답 전송을 정상 종료하면 진행 중 참조가 모두 해제된 뒤 삭제한다. 전송 실패/접속 중단이면 TTL 내 재시도 가능하고, 다운로드하지 않아도 기본 60분 후 만료한다. 동시 요청은 정리 상태와 직렬화하여 삭제 예정 결과에 새 전송을 시작하지 않는다.
- 서버의 전송 완료는 사용자가 실제 디스크에 저장했다는 보장이 아니다. 로그/화면은 `전송 완료`라고 표기하며 `사용자 저장 완료`라고 주장하지 않는다. 보관 N의 즉시 전송 후 삭제/임시 TTL은 다운로드를 가능하게 하기 위한 제안 동작으로 화면에도 고지한다.
- 만료 시각부터 새 preview/download를 거부한다. 실제 삭제는 시작 시 및 5분 주기 정리에서 수행하여 정상 유휴 파일은 만료 후 최대 한 주기 내 제거한다. 실행 중 변환·진행 중 전송은 유한 시간 내 종료 후 삭제한다. 삭제 실패는 로그와 재시도로 남기고 성공한 것으로 처리하지 않는다.
- 원본/Markdown을 각각 정리하며, 둘 다 제거된 종료 작업만 메타데이터와 빈 디렉터리를 정리한다. 파일 정리가 감사 로그까지 지우지는 않는다. 정리 작업은 멱등적이며 DB와 파일 상태가 불일치하면 재시작 후 복구한다.

### 4.2 로그와 마운트 계약

Compose의 관련 부분(전체 실행 파일이 아닌 계획 예시):

```yaml
services:
  app:
    env_file: .env
    volumes:
      - ./data:/data
      - ./logs:/logs
```

- `/logs/access.log`: 모든 서버 HTTP 요청의 수신/종료/중단, 로그인 화면 접근, 상태 폴링, healthcheck, preview/download/API 접근, 인증 실패 요청까지 기록한다.
- `/logs/audit.log`: 최초 계정 생성·재설정, 로그인 성공/실패·세션 만료·로그아웃, 업로드 접수/거절/중단, 변환 대기/시작/성공/실패/timeout, 다운로드 시작/전송 완료/중단, 수동 삭제, 자동 정리 시작/종료·파일별 삭제 성공/실패, 서버 시작/종료/복구, 설정 검증 오류와 비밀이 아닌 보관 정책 적용, 로그 회전/정리 이벤트를 기록한다.
- 서버가 관찰할 수 있는 모든 행위를 기록한다는 의미다. 브라우저의 파일 선택/복사 버튼은 필요 시 인증된 UI 이벤트로 별도 전송하되 클라이언트 보고로 표시한다. 실제 로컬 저장/클립보드 내용/브라우저 강제 종료 등 관찰할 수 없는 행위를 성공으로 기록하지 않는다.
- JSON Lines 형식으로 UTC 시각, 수준, 이벤트, request ID, job ID, 내부 소유자 ID, 신뢰된 접속 IP, 메서드/경로 템플릿, 상태 코드, 처리 시간, 바이트 수, 결과/안전한 오류 코드를 기록한다. 최초 로그 기록 전에 외부 문자열을 구조화·길이 제한해 줄바꿈 로그 위조를 방지한다.
- 비밀번호/해시/쿠키/세션 토큰/CSRF 토큰/Authorization 헤더/전체 `.env`/요청·응답 본문/문서 내용/원본 파일명은 기록하지 않는다. 파일은 job ID로 추적한다. URL 쿼리나 경로의 임의 문자열도 그대로 남기지 않는다.
- 자식 프로세스의 결과는 부모 프로세스가 받아 감사 로그에 쓴다. HTTP access 로거와 앱 로거의 중복/누락을 테스트한다. 회전은 단일 웹 프로세스가 담당한다.
- 기본 제안: 파일당 10 MiB에서 회전, 각 로그 종류당 최대 회전 파일 10개, 회전 파일 최대 30일 보관. 날짜 경계에서도 회전해 조용한 서버의 오래된 활성 로그도 정리한다. 개수/용량 제한에 의해 30일 전에 지워질 수 있으며 30일은 최소 보존 보장이 아니다. 회전 파일도 `./logs` 안에 둔다.
- 데이터 삭제와 로그 삭제는 다른 정책이다. 로그 보관 정리는 정책 이벤트 한 건으로 기록하고 그 로그가 다시 정리 이벤트를 무한 생성하지 않게 한다.
- 호스트 logs 디렉터리의 비루트 UID/GID 쓰기 권한을 확인한다. 시작 시 마운트/쓰기 검증 실패는 서비스 준비 실패로 처리한다. 실행 중 기록 실패는 stderr 비상 알림 + readiness 실패 + 새 변경 작업 접수 중단으로 표시한다. 이미 실행 중인 작업 종료와 안전한 파일 정리는 계속 시도하고 복구 후 누락 가능 구간을 기록한다. 디스크 장애/강제 종료 시 무손실 감사를 보장한다고 주장하지 않는다.
- 컨테이너 재생성 후에도 호스트 로그가 남아야 한다. 업로드/Markdown 보관 N이어도 로그는 유지한다. `.env`, `data/`, `logs/`는 Git 및 Docker build 컨텍스트에서 제외한다.

- 진행률 퍼센트와 Markdown HTML 렌더링은 구현하지 않는다. 화면은 업로드 용량, 지원 형식, 원본/결과 보관 정책을 명시한다.
- 완료: 데스크톱/모바일 폭에서 전체 흐름 사용 가능, 문서/파일명에 포함된 HTML·스크립트가 실행되지 않음, 완료/만료/로그아웃 후 불필요한 폴링 중단.

### P5 — Docker 및 도메인 배포 구성
- 신규 예정: `Dockerfile`, `compose.yaml`, `.dockerignore`, `.env.example`, `docs/web-deployment.md`.
- Python 3.12 기반 이미지, 잠긴 의존성 설치, 비루트·자원 한도·healthcheck·데이터 볼륨·`./logs:/logs` 바인드 마운트·`.env` 최초 비밀번호/보관 설정·세션 secret 파일 주입·프록시 연결 예시를 만든다(E5, E13).
- 컨테이너에서 Tk/디스플레이 없이 웹 서버가 실행되고 설치된 패키지에 템플릿/정적 자산이 포함되는지 검사한다.
- 완료: 새 이미지 build/up/health 성공, 재시작 후 계정과 완료 결과 유지, 미완료 작업 interrupted 처리, 외부 앱 포트 접근 불가, HTTPS 쿠키와 리다이렉트 정상.

### P6 — 통합 검증과 운영 문서
- 대상: `tests/web/`, `tests/integration/`, `docs/web-deployment.md`, `README.md`, 필요 시 `.github/workflows/`의 Docker 검사 전용 작업.
- 백업은 계정/설정 DB 중심으로 제한하고 임시 문서는 기본 제외한다. 업데이트 전 DB 백업/복원과 이미지 rollback 절차를 기록한다.
- 기존 CI/배포 자산은 삭제하지 않는다. 이미지 push, DNS/실서버 변경, 버전·태그·릴리즈는 별도 요청 범위로 남긴다.
- 완료: 아래 수용 기준 및 lint/typecheck/회귀/컨테이너 smoke 결과를 기록하고 미검증 배포 항목을 명시한다.

구현 시 실행할 명령: `uv run --locked --group dev pytest -q`, `uv run --locked --group dev ruff check .`, `uv run --locked --group dev mypy`. 웹 extra는 구현에서 정한 설치 옵션으로 활성화한다. 이후 값을 출력하지 않는 `docker compose config --quiet`, 이미지 build, 격리된 시험 환경의 up/health/login/upload/download/restart 검증을 순서대로 수행한다. `.env` 값을 펼쳐 출력하는 config/env 명령은 검증 로그에 남기지 않는다. 런타임 의존성 취약점 확인도 포함하되 검사 도구 설치는 별도 의존성 검토를 거친다.

## 7. 위험·완화 및 미확인 사항

- 인증을 붙여도 업로드 문서가 안전해지는 것은 아니다 → 크기/압축/시간/프로세스/저장량 한도, rootfs 제한, 개인 계정 전제. 강한 보안 격리를 보장하지 않는다.
- 최초 비밀번호/세션 키/계정 DB 유출 → `.env`/secret 파일의 최소 권한, 이미지·로그·Git 제외, 최초 설정 후 비밀번호 환경 제거, reset/전체 세션 폐기 절차.
- 보관 Y 또는 접근 로그로 디스크가 증가함 → 원본/결과 독립 만료 + 로그 회전/최대 보관기간 + 저장량 한도. 파일 삭제 로그도 남기되 파일 만료가 감사 로그를 삭제하지는 않는다.
- 작은 서버에서 변환이 느리거나 OOM 발생 → 기본 동시성 1, 실제 fixture/큰 문서 측정 후 한도 조정. 일괄 처리와 다중 워커는 제외.
- 프록시/도메인 배치 미확인 → 실제 배포 전에 프록시 위치·인증 존재 여부·호스트 자원을 확인한다. 코드 계획은 이 정보 없이 진행 가능하나 실서비스 검증은 대체할 수 없다.
- 기존 문서가 로컬 앱을 전제함(E5) → 구현 P1에서 웹/로컬 계약을 분리한다. 이번 계획만으로 README의 기존 약속을 변경하지 않는다.
- 참고 프로젝트는 구현 패턴이지 보안 인증된 템플릿이 아님 → E8–E11의 차이를 명시하고 코드 복사 대신 작은 경계별 구현. 가져오는 코드/자산이 있으면 라이선스 고지 확인.

## 8. 이번 계획 작업의 검증 범위

- 두 저장소의 코어·인증·라우트·템플릿·Docker·관련 테스트 소스를 읽고 근거 위치를 확인했다.
- 공식 Starlette/FastAPI/OWASP 문서를 확인했다. 선택할 런타임 버전과 보안 패치 상태는 구현 시 lock 기준으로 다시 확인한다.
- 참고 저장소의 `.env`, 데이터베이스, 사용자 업로드/다운로드 내용은 읽지 않았고 참고 저장소를 수정하지 않았다.
- 계획 문서만 작성·수정했다. 테스트·빌드·실제 도메인 접속은 실행하지 않았으며 서비스 구현 완료를 의미하지 않는다.
